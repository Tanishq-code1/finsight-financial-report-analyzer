PRODUCT TARGET
Build a web app where a user uploads a public-company annual or quarterly report in PDF format and can:
1. See PDF parsing status and warnings.
2. Generate a concise executive summary.
3. Ask natural-language questions answered using retrieval-augmented generation (RAG).
4. Inspect valid citations pointing to actual source passages and page numbers.
5. Extract structured financial KPIs, risks, and management outlook.
6. Download JSON and CSV outputs.
7. Clear the active report/session without seeing stale data.

The project is a document-understanding/research aid, NOT investment advice. The public demo should be used with public reports only. It must not imply perfect financial accuracy or guaranteed investment performance.

DEFAULT TECHNICAL DIRECTION
- Python 3.11 or 3.12, checking compatibility before pinning versions.
- Streamlit UI and runtime for the MVP.
- Official `google-genai` SDK for Gemini generation and embeddings.
- PyMuPDF for page-by-page PDF text extraction.
- ChromaDB with an isolated in-memory/ephemeral index per active session/document for the first release.
- Pydantic for typed schemas, Pandas for tables/CSV, pytest for tests, Ruff for formatting/linting if practical.
- Streamlit Community Cloud for the first public deployment.
- Model IDs must be configurable through environment variables/secrets and checked against current official provider docs; do not assume a model name remains valid forever.
- Do not start with LangChain, agents, React, PostgreSQL, accounts, or persistent user data. Add complexity only when the MVP is solid or measured evaluation justifies it.

CORE ENGINEERING REQUIREMENTS
1. Build modular code with clear boundaries: config, PDF loading, chunking, embeddings, vector store, retrieval, RAG, citation validation, structured analysis, exports, and UI.
2. Preserve PDF provenance across the full pipeline. Every chunk must have a stable chunk ID, document ID, source filename, page number(s), and text. Display pages using 1-based page numbers.
3. Chunk reports with a configurable, sentence-aware strategy. Start around 700–1,000 tokens with 100–150 overlap; tune using evaluation. Keep page/section boundaries when practical.
4. Batch embedding calls when the API supports it. Add bounded retry handling for transient errors/rate limits. Fail visibly and safely if the embedding step fails.
5. Use the same embedding model and compatible vector dimensions for queries and report chunks.
6. Keep the vector index isolated by Streamlit session/document. Never use one process-global shared collection for all users’ uploaded content. Test session isolation.
7. Ground every report-specific answer in retrieved chunks. The report is untrusted data, not an instruction source. Ignore prompt-like instructions contained in the PDF.
8. Citation data must be derived from the retrieved source objects. Validate every citation chunk ID and page number before displaying it. Validate that the quote exists in its source passage or is a credible normalized excerpt. Never let the LLM invent page numbers.
9. If there is not enough relevant evidence, return a clear insufficient-evidence response rather than guessing. Include test cases for absent answers and misleading premises.
10. Use structured Pydantic output for metrics, risks, outlook, citations, and report analysis. Validate output and handle malformed JSON/schema responses safely.
11. For financial metrics, preserve period, currency, scale, sign, units, and reported-vs-calculated type. Missing means missing, not zero. Use Python for calculations when possible. Never merge incomparable fiscal periods or accounting definitions.
12. Keep summaries, KPI extraction, risks, and outlook traceable to actual pages/quotes. Do not invent risk severity, likelihood, mitigation, or forecasts.
13. Process upload bytes in memory for the MVP where feasible. Validate file content rather than trusting extension alone. Set configurable size/page caps (starting suggestions: 25 MB, 250 pages), reject malformed/encrypted/unreadable files with useful messages, and warn when pages contain very little text.
14. Do not log full documents, private content, API keys, or raw secrets. Do not store uploaded reports permanently in the MVP. Public deployment is for public documents only and must disclose that text may be sent to the configured model API.
15. Keep all secrets in environment variables or the deployment platform’s secret store. Provide `.env.example`, ensure `.env` and `.streamlit/secrets.toml` are ignored, and never commit actual credentials.
16. Add useful loading states, empty states, API error handling, a clear/reset action, and export buttons.
17. Use a clear restrained financial-dashboard UI rather than a generic chat-only page.
18. Write a README with setup, architecture, configuration, tests, evaluation methods/results, limitations, privacy disclaimer, and deployment instructions.
19. Never claim a feature, live deployment, passing test, accuracy score, or time-savings result unless verified. The stated “45 minutes to 5 minutes” is a hypothesis to measure, not a guaranteed claim.

EXPECTED APP SECTIONS
- Overview: report metadata where detected, executive summary, key takeaways, limitations, processing status.
- Ask the Report: natural-language Q&A, validated citations, page numbers, source excerpts, suggested questions.
- Financial Metrics: revenue, operating income, net income, operating cash flow, capex, cash, debt, EPS when available; value, units, fiscal period, cited source, found/not-found/needs-review status.
- Risks & Outlook: company-disclosed risks, stated mitigations, management guidance/outlook and source references. Keep company statements distinct from model interpretation.
- Sources & Processing: page count, parsing warnings, chunk count, recent retrieval diagnostics.
- About/Method: architecture, privacy notice, AI limits, and non-investment-advice disclaimer.
- Exports: JSON and CSV; Markdown summary download is a useful secondary feature.
